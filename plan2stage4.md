# Задание агента — Этап 4. Админка («панель мастера»)

**Тип задачи:** авторизация + CRUD-админка (страницы из макета 1:1) + API + загрузка изображений + Telegram-уведомления
**Зависимости:** `plan2stage1.md` … `plan2stage3.md` выполнены и приёмлены (проект в `site/`: Next.js 16.3.1 + TS + Drizzle + SQLite; seed-данные в БД; публичные страницы и API `/api/orders`, `/api/contact` работают)
**Связанные пункты плана:** `plan-2.md` §2 (карта соответствия: admin/*.html), §3 (D-8, D-10, D-12, D-13, D-14), §4 (Auth.js), §6 (маршруты админки, API `CRUD /api/admin/*`, `POST /api/upload`, `POST /api/admin/settings/telegram-test`), §8 Этап 4 (T-4.1 … T-4.6), §9 (Q-4)
**Версия плана:** plan-2.md (итерация 2) — единственная действующая

---

## Цель

Реализовать админку «панель мастера» как «копия макета 1:1 + данные из БД»:

1. вход по одному аккаунту (логин/пароль из env, D-12) и защита `/admin` и `/api/admin/*`;
2. 7 страниц из `mockup/admin/*.html`: login, dashboard, products, components, categories, orders, settings;
3. CRUD-API под ними, загрузка изображений (`/api/upload`), кнопка «Тест» Telegram и реальные уведомления о заявках.

Приёмка этапа (из плана): **владелец управляет всем контентом без правок кода; страницы админки повторяют макет**.

## Золотые правила (§0 плана) — обязательны

1. `mockup/` — **источник истины**. Структура HTML, CSS-классы, тексты, иконки (inline-SVG) переносятся копированием 1:1. Никаких Tailwind/shadcn и прочих UI-фреймворков (D-2). Все классы админки уже есть в `style-memphis.css` / `style.css` — **CSS не трогаем вообще**.
2. **Запрещено**: переделывать вёрстку, придумывать свои компоненты/дизайн/тексты/поля, «улучшать» одобренное.
3. Чего нет в макете — не додумывать; при блокере остановиться и записать вопрос руководителю (в отчёт), а не решать самостоятельно. Спорные места перечислены в «Вопросах руководителю» с предложенными дефолтами: работаем по дефолтам, фиксируем в отчёте.
4. Файлы `mockup/**` не редактировать — только читать. CSS/JS скинов не трогать.
5. **D-11:** демо-цифры админ-макетов — демонстрационные. Источник данных — БД (seed по публичным страницам). Пример: «Кулоны» в редакторе категорий показывают 1 000 ₽ / 3 дн из БД, а НЕ 1 400 ₽ / 5 дн из `admin/categories.html`.
6. **D-3:** пометки «sharp» в макетах админки — устаревшие, игнорировать (никакой sharp-обработки изображений на этом этапе).
7. Коммиты — только по явной команде руководителя.

Если npm ругается на peer-зависимости — установить с `--legacy-peer-deps` и зафиксировать версию в отчёте. `AUTH_SECRET` — обязательный env (сгенерировать, например `openssl rand -base64 32`).

- Изменений схемы БД на этом этапе **нет** (поля `availability/reserveUntil/orderDays/meta*` уже есть с этапа 1; `materials/specs` — с этапа 3).

## Шаг 1 (T-4.1). Auth.js: вход и защита

1. **Установка:** `npm i next-auth@beta` (≥ 5.0.0-beta.30). `lib/auth.ts` (server-only):
   - `Credentials` provider: `authorize(credentials)` сверяет `login`/`password` со `process.env.ADMIN_LOGIN` / `process.env.ADMIN_PASSWORD` (**из env, не из кода** — D-12); неверные → `null` (без подсказки, что именно неверно);
   - `session: { strategy: "jwt" }`, `pages: { signIn: "/admin/login" }`, `AUTH_SECRET` из env;
   - экспорт `{ handlers, auth, signIn, signOut }`.
2. **Route handler:** `app/api/auth/[...nextauth]/route.ts` → `export const { GET, POST } = handlers`.
3. **`/admin/login`** — копия `mockup/admin/login.html` 1:1 (без демо-заполнения `value="julia"`/`value="b4k3lit-76"` — это демо-данные макета; поля пустые, с placeholder'ами «Логин»/«Пароль»):
   - `body class="login-page"` → на сайте класс вешаем на обёртку `<div className="login-page">` (класс в CSS — plain-селектор, проверено);
   - `div.logo-big` «JulCraft», `p.sub` «// панель мастера · только для своих», `div.receipt` с `h2` «◍ ВХОД ДЛЯ МАСТЕРА ◍», `div.err-box` «✘ Неверный логин или пароль — попробуйте ещё раз» (**рендерится только после неудачной попытки**), поля Логин/Пароль (пароль — `type="password"`), `button.btn.btn--primary.btn--block` «Войти в мастерскую», `p.thanks` «*** один аккаунт · никакой рекламы ***», `div.barcode`, `p.sub` «← Вернуться на витрину» → `/`;
   - форма — клиентский компонент: server action `loginAction` (в `app/admin/login/actions.ts`) вызывает `signIn("credentials", { redirect: false, ... })`; при ошибке — `useActionState` возвращает «ошибка», показываем `err-box`; при успехе — `redirect("/admin")`;
   - `<title>` «Вход — JulCraft Админ».
4. **Защита страниц:** `app/admin/(panel)/layout.tsx` (роут-группа, чтобы login был снаружи):
   - серверная проверка `auth()` → нет сессии → `redirect("/admin/login")`;
   - рендерит `AdminHeader` (копия topbar + mobile-menu из admin-макетов: `a.logo` «JulCraft<small>панель мастера</small>» → `/admin`; nav: Дашборд `/admin`, Товары `/admin/products`, Склад `/admin/components`, Категории `/admin/categories`, Заявки `/admin/orders`, Настройки `/admin/settings` с `is-active` по маршруту; `a.icon-btn.icon-btn--rust` «⏻» `title="Выйти"` → server action `logoutAction` (`signOut({ redirect: false })` → `redirect("/admin/login")`); бургер + мобильное меню: `mm-head` «Панель мастера» + «✕», 6 ссылок `a.mm`, `mm-foot` «Выйти →»);
   - маршруты внутри группы: `/admin` (dashboard), `/admin/products`, `/admin/components`, `/admin/categories`, `/admin/orders`, `/admin/settings`.
5. **Защита API:** в каждом `app/api/admin/*` route handler — `const session = await auth(); if (!session) return Response.json({ error: "Не авторизован" }, { status: 401 });` (можно вынести в `lib/admin.ts` хелпер `requireAdmin()`).
6. **env:** в `.env.example` (и в локальном `.env`) добавить: `AUTH_SECRET=` (сгенерированный), комментарий, что `ADMIN_LOGIN`/`ADMIN_PASSWORD` теперь используются (D-12). Значения для локальной разработки — см. Вопрос 1.

## Шаг 7 (общий). Загрузка изображений

1. **`POST /api/upload`** (только для авторизованных, `requireAdmin()`):

6. Заявки: фильтры по статусу/типу работают; модалка показывает клиента/контакт/комментарий, чек состава (для custom — строки из configJson, для product — товар, для contact — сообщение), смена статуса работает и видна в таблице; заявки type=contact имеют бейдж «контакт» (D-14).

## Вопросы руководителю (не блокирующие — работать по предложенному, фиксировать в отчёте)

1. **Креды для локальной разработки.** D-12: логин/пароль из env, не из кода; в макете демо-пара `julia` / `b4k3lit-76`. Предложение: в локальный `.env` записать именно их (совпадает с демо, удобно показывать заказчику), `AUTH_SECRET` сгенерировать; на проде (Этап 7) — свои значения. Альтернатива: любые другие значения от руководителя.
2. **Саблайны метрик дашборда.** Демо-подписи («+3 к прошлой · пик в субботу», «2 кулона · 1 комплект») невычислимы. Предложение (D-10): «Товаров на витрине» — `{N}` + sub «из них {n} новинок · {m} в резерве»; «Заявок за неделю» — count за 7 дней + sub «+{n} к прошлой неделе» (при 0 — «как на прошлой неделе»); «В работе сейчас» — count `in_progress` + sub «в работе: {n}»; «Выручка за неделю» — Σ `calcPrice` заявок `done` за 7 дней + sub «из них {n} ₽ — конфигуратор» (Σ custom done). Альтернатива: оставить демо-тексты 1:1 (вводит в заблуждение — не рекомендую).
3. **Бейдж «контакт» и фильтр.** D-14 требует бейдж «контакт» в таблице заявок; в макете его нет. Предложение: бейдж `tag tag--olive` «контакт» + третий фильтр в ряду типов «Контакт (N)». Альтернатива: без фильтра, только бейдж.
4. **Мелкие UX-дополнения без макета.** (а) «✎» в строке заявки: модалки редактирования нет — предложение: открывает ту же модалку деталей (внешне ничего нового); (б) удаление фото товара в табе «Фото»: предложение — «✕» (`icon-btn`, 20px) в углу миниатюры; (в) подтверждение удалений — нативный `confirm()`. Альтернативы: не рендерить «✎»; не давать удалять фото.
5. **Слоты: имя и порядок.** (а) В макете редактор слотов не показывает поле имени (слоты именованы: «Основной камень»…). Предложение: добавить поле «Название» в `slot-body` (необходимо для конфигуратора; минимальное расширение формы, классы те же). (б) Drag&drop категорий — предложение: нативный HTML5 DnD на `slot-head` (без библиотек); альтернатива: кнопки «↑/↓» как у слотов (в макете у категорий их нет — хуже).
6. **Форма настроек vs JSON в БД.** `contacts.hours` и `about.*` хранятся JSON-массивами (решение этапа 2), а макет показывает textarea с текстом/пару полей «будни/выходные». Предложение: (а) часы — 4 отдельных поля (Понедельник / Вторник — Пятница / Суббота / Воскресенье), собираются в `contacts.hours` при сохранении; (б) `about.short/history` — редактор строк чеков (динамические поля «метка — значение» + thanks); (в) `about.principles` — 4 карточки (title + text). Классы только `.field`/`.field--row`/`.checkbox` — новый дизайн не придумываем. Альтернатива: textarea с JSON + валидация парсинга (проще, но хрупко для владельца — не рекомендую).
7. **Пагинация и размеры страниц админки.** Демо-макеты противоречивы (products: 12 строк → страницы 1–4 из 41; components: 25 строк → «1 2»; orders: 9 строк → «1 2»). Предложение: единообразно — products/components `pageSize=12`, orders `pageSize=10`, пагинацию показывать только при >1 странице (как на публичной категории, решение этапа 3). Альтернатива: повторять демо-раскладку страниц 1:1 (не рекомендую — цифры демо).
8. **Порог «Склад: что кончается».** План (T-4.x) говорит «остаток ≤ 5 шт», а демо dashboard.html показывает чипы с 8 и 10 шт. Предложение: по плану — `stockQty ≤ 5` (0 шт — `chip--rust`, 1–5 — `chip--mustard`), плюс `chip--olive` «Остальное — в норме». Альтернатива: порог 10 как в демо.
