# Задание агенту — i18n-2 · Шаг 2 из 8: Миграция данных БД в {ru: ...}

**Тип задачи:** миграция данных
**Зависимости:** i18n-2 · Шаг 1 (тип LocalizedString, firstLocale)
**Связанные пункты плана:** `plan-3.md` §4 (i18n-2: конвертация одиночных строк в {ru})
**Затрагиваемые таблицы:** `categories` (name, description), `slotTemplates` (name), `componentTypes` (name), `components` (name), `products` (name, description, metaTitle, metaDescription), `settings` (JSON-поля с текстами)

## Цель

Все текстовые поля контента хранятся как `{"ru": "..."}` (или legacy-строка — валидны оба, helper их ест). Схема таблиц не меняется (поля уже text/JSON-compatible) — конвертируются только данные. Сид обновляется для новых БД.

## Важно

- **Сначала бэкап:** `npm run snapshot:capture` (скрипт есть) — точка отката.
- Миграцию оформить отдельным скриптом `scripts/migrate-locale.ts` (по образцу существующих `scripts/migrate-*.ts`), одноразовая, идемпотентная (повторный запуск — no-op).
- **Схема БД не меняется** — Drizzle-миграций не требуется, только данные. Формат хранения: объект `{ru}` (не просто строка) для единообразия; legacy-строки в БД допустимы, но после миграции их не остаётся.

## Шаги

1. Скрипт `scripts/migrate-locale.ts`:
   - таблицы/поля по списку выше; `settings` — только ключи с текстами (about.*, contacts.address, finance.currencies[].name и т.п. — перечень ключей взять из `lib/settings.ts` / `scripts/seed.ts`, список в отчёт);
   - конвертация: строка без локали → `{ru: строка}` (JSON.stringify); уже объект → пропустить (идемпотентность);
   - валидация после записи: каждое значение парсится и `L(v, "ru") === исходная строка` (гарантия сохранения RU-вывода).
   - БД как backups: перед запуском на локальной БД — snapshot.
2. `scripts/seed.ts`: все текстовые значения сущностей — в формате `{ru: "..."}` (данные те же). `npm run check:seed` (есть) должен проходить — при необходимости обновить ожидания чекера, если он сравнивает строки напрямую (зафиксировать в отчёте).
3. Прогон на dev-БД: snapshot → migrate → проверка сайта (RU-витрина визуально не изменилась) → `check-snapshot` / ручная сверка страниц.
4. Валидация перечня Settings-ключей с руководителем ДО запуска (текст в отчёте шага, не отдельный вопрос — выполнить по best-effort, руководитель ревьюит приёмку).

## Критерии приёмки

1. RU-витрина и RU-админка после миграции показывают те же тексты, что до (сверка страниц каталога/товаров/конфигуратора/главной/о мастерской + списка категорий админки).
2. Повторный запуск `migrate-locale.ts` — no-op (идемпотентность).
3. `npm run check:seed` зелёный; новый сид разворачивает БД с `{ru:...}`.
4. `npm run lint`, `npm run build`.

## Не делать (out of scope)

- Вывод через L() на страницах (шаги 3–6) — после миграции страницы продолжают показывать RU, т.к. `L` ест оба формата. Поля EN/UK в админке (шаг 7). SEO-автогенерация (шаг 8).
