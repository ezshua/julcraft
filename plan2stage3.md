# Задание агента — Этап 3. Публичная часть сайта

**Тип задачи:** страницы / UI из макета + API заявок (product/contact)
**Зависимости:** `plan2stage1.md` и `plan2stage2.md` выполнены и приёмлены (проект в `site/`: Next.js + TS + Drizzle + SQLite; seed-данные в БД; `lib/settings.ts` читает Settings с фолбэком на дефолты макета)
**Связанные пункты плана:** `plan-2.md` §2 (карта соответствия), §3 (D-7, D-9, D-13, D-14), §6 (API: POST /api/orders, POST /api/contact), §8 Этап 3 (T-3.1 … T-3.5)
**Версия плана:** plan-2.md (итерация 2) — единственная действующая

---

## Цель

Реализовать все публичные страницы сайта как «копия макета 1:1 + данные из БД»:

1. Главная `/` (витрина, плитка категорий, CTA, чек-тизер, часы);
2. Каталог `/catalog` и категория `/catalog/[slug]` (фильтры, сортировка, пагинация, скелетон, пустое состояние);
3. Карточка товара `/product/[slug]` (галерея, чипы, характеристики, модалка заявки, «Собрать похожий →», «Рядом на полке»);
4. Конфигуратор `/configurator` (список категорий);
5. `/about`, `/contacts` (форма обратной связи → Order type=contact), `/order-success/[id]`, `/404`.

Приёмка этапа (из плана): **все публичные страницы визуально совпадают с макетом; заявка на товар пишется в БД**.

## Золотые правила (§0 плана) — обязательны

1. `mockup/` — **источник истины**. Структура HTML, CSS-классы, тексты, иконки (inline-SVG) переносятся копированием 1:1. Никаких Tailwind/shadcn и прочих UI-фреймворков (D-2).
2. **Запрещено**: переделывать вёрстку, придумывать свои компоненты/дизайн/тексты/поля, «улучшать» одобренное.
3. Чего нет в макете — не додумывать; при блокере остановиться и записать вопрос руководителю (в отчёт), а не решать самостоятельно.
4. Файлы `mockup/**` не редактировать — только читать. CSS/JS скинов не трогать.
5. Статичные **демо-блоки** макета — это компоненты для реальных состояний сайта, а НЕ декорации: демо «пустое состояние» (catalog.html) → компонент `EmptyState` для пустой категории; демо «скелетон» (category.html) → `loading.tsx` роута категории. **На публичных страницах эти демо-секции не рендерить.**
6. Коммиты — только по явной команде руководителя.

## Решения заказчика (зафиксированы руководителем — работать строго по ним, в «Вопросы руководителю» не возвращаться)

- **R-1. Витрина главной:** сначала `isFeatured` (по `sortOrder`/`id`), затем `isNew`, затем остальные; **лимит 12** карточек (как «12 штук на полке» в макете). Подзаголовок секции копируется 1:1.
- **R-2. Чипы и характеристики товара — поля в БД:** расширить таблицу `products` (миграция): `materials` (json `text[]` — чипы) и `specs` (json `text[]` — строки характеристик). Значения для «Кулона Телеграмма» — **дословно из `mockup/product.html`**: materials `["стекло","латунь","гравировка"]`, specs `["Размер: 32 × 24 мм, толщина 8 мм","Цепочка латунная 50 см в комплекте","Вес: 11 г — лёгкий, как утренние планы","Уход: протирать фланелью, не ронять на асфальт"]`. У остальных товаров — пустые массивы; блоки чипов и списка не рендерим, если массив пуст. Доработать `scripts/seed.ts` (новые поля для Телеграммы; у остальных — `[]`). Оформить запись о расширении схемы для «Журнала изменений» plan-2.md (в отчёте).
- **R-3. Чек заявки по типу:** `/order-success/[id]` показывает строки по типу заявки (см. Шаг 3.3). Форма /contacts после успешной отправки редиректит на `/order-success/[id]` (чек type=`contact`).

- Макет — `mockup/` (корень репо), сайт — `site/` (макет туда не копируем). Сверка приёмки — с `mockup/*.html` построчно.
- БД наполнена (этап 2): 10 категорий, слоты, 25 комплектующих, 19 товаров, Settings (контакты, часы, about.*).
- `lib/settings.ts` (этап 2): чтение значений из таблицы `settings` с фолбэком на дефолты макета. Проверить, что Header/Footer (этап 1) уже берут контакты/часы из Settings; если нет — доработать (подписи дней футера — статичные из макета футера: «Понедельник / Вт — Пт / Суббота / Воскресенье», значения — из `contacts.hours` по индексу).
- Цены в БД — целые рубли (не копейки). Формат на страницах — как в макете: `1 950 ₽` (неразрывный пробел-разделитель тысяч, `ru-RU`).
- Изображения: **обычные `<img>`** с атрибутами из макета (`loading="lazy" decoding="async"`, query `w=800&q=80` на полке, `w=900` главное фото, `w=300` миниатюры). `next/image` НЕ использовать — это Этап 6 (T-6.3). В БД URL хранится с `w=800&q=80`; при рендере галереи подменять query на `w=900`/`w=300` (маленькая утилита в `lib/format.ts`).
- Маршруты и метаданные: каждая страница — `metadata` c `<title>` из макета (примеры: `Каталог — JulCraft`, `Кулоны — JulCraft`, `Кулон «Телеграмма» — JulCraft`, `Конфигуратор — JulCraft`, `О мастерской — JulCraft`, `Контакты — JulCraft`, `Заявка принята — JulCraft`, `Страница не найдена — JulCraft`). SEO-таб из БД — Этап 6, не делать.
- Динамические роуты: несуществующий slug/номер → `notFound()` (рендерит наш `/404`). `searchParams` в Next 15+ — Promise, не забыть `await`.
- Ссылки на ещё не созданные роуты ставим как в макете: «Собрать похожий →» → `/configurator/[categorySlug]` (D-9, страница появится на Этапе 5), «⏻» в шапке 404 → `/admin/login` (Этап 4). Клик по ним даст 404 — это нормально на промежуточном этапе.
- Уведомления мастеру (Telegram) — заглушка `console.log`; реальная отправка — Этапы 4.6/5.4 (нужны токены Q-4).

## Вопросы руководителю (не блокирующие — работать по предложенному, фиксировать в отчёте)

1. **Подписи категорий.** Плитка главной показывает короткие строки («стекло, эмаль, янтарь»), которых нет в БД (там полное описание «стекло, эмаль, янтарь. На цепочке…»), а подписи конфигуратора («3 слота: камень, подвески, основа», «как серьги + брошь») не выводятся из данных слотов. Предложение: статичные строки 1:1 из макета (маппинг по slug). Альтернатива: производные от данных (первое предложение description; список типов слотов) — даст отличия от макета.
2. **Галерея товара.** В БД 1 фото на товар, в макете — 4 миниатюры (2 фото + 2 SVG-эскиза). Предложение: показывать N фото (до 4), слоты до 4 добивать SVG-эскизами из макета. Альтернатива: только реальные фото (галерея из 1 миниатюры).
3. **Пагинация.** pageSize = 9 (первая страница макета — 9 карточек). Предложение: показывать только при >1 странице. Альтернатива: всегда (как в макете).
4. **`out_of_stock` на полке.** В публичных макетах не показан. Предложение: `<span class="avail">✕ нет на складе</span>`. Альтернатива: не выводить такие товары в выборках.
5. **СТАТУС в чеке** для не-new статусов. В макете только «новая · в очереди к верстаку». Предложение: `in_progress` → «в работе», `done` → «готова», `cancelled` → «отменена» (словами, по смыслу бейджей админки). Альтернатива: показывать латинские коды статусов.
