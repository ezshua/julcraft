# Предложения по внедрению мультиязычности (i18n)

**Контекст.** Сайт JulCraft — Next.js (App Router). Сейчас весь текст на русском и
захардкорен в страницах/компонентах, кроме блока «Тексты» (`Settings.about.*`:
чек-строки `short`/`history` и `principles`), который редактируется в админке и хранится
в таблице `settings` (key/value JSON). Валюты уже мультивалютные (`FinanceSettings`),
но язык единый. Полный реестр строк — в `i18n-audit-strings.md`.

Ниже — идеи и конкретный план, **без изменения существующего кода** (пока только анализ
и проект решения).

---

## 1. Два независимых слоя текста

Смешивать редактируемый копирайт и UI-переводы в одну кучу — ошибка. Предлагаю разделить:

### Слой A — «Контент» (редактируемый копирайт)
То, что владелец правит в админке и что осмысленно как «текст сайта»: слоганы, заголовки
секций, маркетинговая проза, thanks-строки чеков, описания категорий, подписи часов.
Сейчас это частично `Settings.about.*`. **Решение:** расширить модель настроек, сделав
значения мультиязычными: `value: { ru: "...", en: "..." }` с обязательным `ru` как fallback.

### Слой B — «UI / переводы» (интерфейс)
Навигация, кнопки, метки форм, статусы заказа, метки чеков, aria, бейджи, placeholders.
Это **не** контент, а стабильный интерфейс. **Решение:** статический словарь переводов
(без админки), один файл на локаль: `messages/ru.json`, `messages/en.json`.

### Слой C — «Локаль» (лингвистика)
Дни недели, правила склонений (`plural`), форматы дат/чисел. Централизовать в i18n-провайдере
(`Intl` + собственные правила для русского/`ru` и будущих языков). **Не редактируется.**

---

## 2. Варианты хранения (сравнение)

| Вариант | Где хранить «Контент» | Плюсы | Минусы |
|---------|----------------------|-------|--------|
| **1. Расширить `settings` (key/value)** | в БД, как сейчас `about.*` | нет новой БД-схемы; админка уже есть | JSON-значения раздуются; нужна миграция структуры значений; тяжело для UI-строк |
| **2. Отдельная таблица `content` (locale, key, value)** | новая таблица в БД | чистая модель; легко добавлять языки и ключи; можно редактировать из админки | нужна миграция + админка для контента |
| **3. MD/JSON-файлы в репозитории** | `content/ru/*.json` | просто, git-история, деплой с кодом | нет редактирования из админки (владелец правит кодом) |

**Рекомендация:** для Слоя A — **вариант 2** (таблица `content`), т.к. владелец хочет
править тексты в админке, а языков будет несколько. Для Слоя B — **файлы `messages/*.json`**
в репозитории (UI переводы правит разработчик, не владелец).

---

## 3. Рекомендованная архитектура

1. **Локаль в URL** — самый SEO-дружественный и простой для Next.js App Router:
   `app/(public)/[lang]/...` либо middleware, добавляющий префикс. Альтернатива —
   cookie `NEXT_LOCALE` + middleware (без смены URL). **Рекомендую URL-префикс** (`/en/...`),
   т.к. это лучше для индексации и явно для пользователя.
2. **Провайдер переводов** — легкий клиент/сервер хелпер:
   - серверный `getT(lang)` → читает `messages/{lang}.json` + `content` из БД;
   - клиентский `useT()` для компонентов `"use client"`.
   - Функция `t("key")` с плейсхолдерами `t("found", { n })` и поддержкой мн. числа.
3. **Fallback** — если ключ/язык отсутствует, берём `ru`. Для Слоя A fallback гарантирован
   (владелец обязан заполнить RU), для Слоя B — `ru.json` полный.
4. **`next-intl` или `next-i18next`?** Можно без библиотеки (проект небольшой), но
   `next-intl` даёт роутинг, форматирование `Intl`, plural из коробки. **Рекомендую
   `next-intl`** — минимизирует свой велосипед, особенно для склонений и дат.

переезжают в Слой A (ключ по slug), чтобы владелец мог править и переводить.

## 5. План внедрения (этапы)

**Этап 0 — Подготовка (без ломки интерфейса).**
- Вынести все строки из аудита в единый список ключей.
- Централизовать дни недели и `plural` в один модуль локали (устранить дубли
  `Footer.tsx:7`, `SettingsPanel.tsx:19`, `settings.ts:52–57`).
- Унифицировать навигацию: `NAV_LINKS` (`nav-links.ts`) + `ERROR_NAV` (`ErrorHeader.tsx`)
  → один источник.

**Этап 1 — Слой B (UI-переводы).**
- Добавить `next-intl`, middleware с префиксом `/[lang]`.
- Создать `messages/ru.json` + `messages/en.json`, обернуть страницы в `NextIntlClientProvider`.
- Заменить хардкод кнопок/меток/статусов на `t("...")` (строки аудита с пометкой `i18n`).

**Этап 2 — Слой A (редактируемый контент).**
- Новая таблица `content` (migrations) + расширение `getSettings`/`SettingsPanel`.
- Перенести `about.*` в новую модель; добавить поля для `home.*`, `category.*`, `contacts.*`,
  `order-success.*` и т.д. (строки аудита с пометкой `Тексты`).
- Админка: вкладка «Контент» с выбором языка и редактором по ключам.

**Этап 3 — Переключатель языка + SEO.**
- В шапке — переключатель `RU | EN`, сохраняющий текущий путь.
- `hreflang`, `alternate` в метаданных, `sitemap` по локалям.

**Этап 4 — Полировка локалей.**
- Склонения и падежи через `next-intl`/`Intl.PluralRules` (для `ru` — своя логика, уже есть
  в `format.ts:plural`).
- Проверка смешанных строк («{address} · Солома», «под заказ · {n} дн») — плейсхолдеры
  внутри переводимых фраз.

## 6. Полный реестр строковых константы (сводно)

Полный перечень с файлами и строками — в `i18n-audit-strings.md` (133 позиции, сгруппированы
по 15 зонам: главная, о нас, контакты, каталог, категория, товар, конфигуратор, успех заявки,
404, шапка/подвал/меню, карточки категорий, форма контакта, карточка/модалка товара, UI-примитивы,
шапка 404). Каждая позиция помечена, куда её отнести: `Тексты` / `i18n` / `Локаль` / `—`.

Краткая статистика по слоям (примерная, для оценки объёма):
- `Тексты` (редактируемый копирайт): ~70 строк → Слой A.
- `i18n` (UI/интерфейс): ~50 строк → Слой B.
- `Локаль` (дни, склонения): ~6 логических блоков → Слой C.
- `—` (символы/техническое): стрелки, разделители — не трогать.

## 7. Особенности и риски

1. **Склонения и падежи (RU).** Массивы `plural` (`день/дня/дней`, `комплект/комплекта/комплектов`,
   `изделие/изделия/изделий`) и дни недели из `format.ts` нужно вынести в локаль и дать
   `next-intl`/`Intl.PluralRules` управлять ими. Для EN правила другие — библиотека закроет.
2. **Смешанный контент.** Строки вида `// {address} · Солома`, `под заказ · {n} дн`,
   `ЧЕК ЗАЯВКИ №{id}` — динамические значения внутри перевода. Хранить шаблон в словаре
   с плейсхолдером, подставлять значение при рендере.
3. **Дублирование (см. аудит).** Перед i18n обязательно устранить тройное дублирование дней
   недели и двойное навигации — иначе перевод придётся править в 2–3 местах.
4. **Адрес/год/слоган.** Сейчас частично в settings (`contacts.address`), частично хардкод
   (Footer, not-found, ErrorHeader). Целесообразно вынести «фирменный блок» в Слой A целиком.
5. **SEO и метаданные.** `<title>` на каждой странице захардкорен (строки аудита №1, 21, 37,
   45, 53, 60, 65, 74, 85) — нужно генерировать через `t()` с учётом локали.
6. **Бэкенд/заказы.** Статусы заказа (`STATUS_TEXT`) используются и в админке, и в квитанции
   клиента — перевод должен быть единым для обоих.
7. **Объём правки.** ~120 публичных строк + админка (вне текущего аудита, но тоже нужна для
   полноты). Админку можно оставить RU-only на первых порах (рекомендую).

---

## 8. Итог

- Копирайт (Слой A) → таблица `content` в БД + админка, значения `{ ru, en, … }`.
- Интерфейс (Слой B) → `messages/*.json` + `next-intl`, без админки.
- Лингвистика (Слой C) → централизованная локаль (`Intl` + правила склонений).
- Сначала устранить дубли (дни, навигация), затем Слой B, затем Слой A, затем переключатель
  и SEO. Никаких изменений в код и планы до старта этапа 0 не вносим.
