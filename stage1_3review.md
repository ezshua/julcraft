## 4.1 Пояснение: warning Next 16 про `lib/db.ts` (п.3)

**Симптом:** при `npm run build` выводится warning вида «Static analysis determined that this filesystem access causes the whole project to be traced and included in the output», со стеком `./lib/db.ts → new Database(...)` и импорт-трейсами `app/api/orders`, `app/api/contact`, `app/(public)/catalog/page` и т.д.

**Причина:** в `lib/db.ts:11-13` путь к файлу БД вычисляется динамически — `resolve(process.cwd(), process.env.DATABASE_URL.slice("file:".length))`. Анализатор Next 16 не может определить, что доступ ограничен конкретной подпапкой, поэтому предполагает доступ к **любому файлу проекта** и включает в серверный бандл-трейс все исходники и `public/`. Warning появляется для каждого потребителя `lib/db`.

**Последствия:** не ошибка — сборка проходит, сайт работает. Практический эффект один: при деплое (Этап 7) в серверный код попадёт лишнее содержимое (весь `site/`, включая `public/`), что раздувает размер и замедляет деплой. На этапе 1–3 это безвредно.

**Варианты устранения (правка кода — только по команде руководителя):**
- (а) `/* turbopackIgnore: true */` на вызове `resolve(...)` — отключает трассировку для этой строки; файл БД в бандле не нужен (он создаётся миграцией на сервере). Минимальная правка, нулевой риск — **рекомендуется**;
- (б) статически ограничить путь: хранить БД в подпапке `site/data/julcraft.db` и резолвить `path.join(process.cwd(), "data", "julcraft.db")` — чище архитектурно, но меняет расположение файла БД (нужно обновить `.env`, `.env.example`, migrate/seed) и не гибко для прода (на VPS путь к БД часто свой);
- (в) ничего не делать до Этапа 7 — warning безвреден на стадии разработки.

## 4.4 Пояснение: id товаров после пересида (п.6, найдено при живом тесте)

**Симптом:** в БД после нескольких `npm run db:seed` id товаров стали 58–76 вместо ожидаемых 1–19; id заявок тоже растут (1-й сид дал заявку id=3, хотя таблица пуста).

**Причина:** `scripts/seed.ts` очищает таблицы (`db.delete(...)`), но не сбрасывает `sqlite_sequence` — счётчик SQLite AUTOINCREMENT хранит максимальный использованный id. `DELETE` не возвращает счётчик назад, поэтому каждый пересид продолжает нумерацию.

**Влияние:** для работы сайта — не баг: URL товаров строятся по `slug`, `OrderModal` шлёт реальный `product.id` из БД, чек читает товар по `productId` из заявки. Проблема проявляется в двух случаях:
1. заявки, созданные до пересида, ссылаются на `productId`, которого после пересида не существует → в чеке заявки СОСТАВ покажется как «—»;
2. непредсказуемые номера чеков и id в dev/демо (вводит в заблуждение при демонстрации).

**Рекомендация (правка кода — по команде руководителя):** в `scripts/seed.ts` после очистки таблиц добавить сброс счётчиков, например:
```ts
db.run("DELETE FROM sqlite_sequence");
```
(таблица `sqlite_sequence` создаётся SQLite автоматически при использовании AUTOINCREMENT; безопасно, т.к. сид всё равно пересоздаёт данные).
