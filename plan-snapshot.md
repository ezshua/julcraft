**Тип задачи:** инфраструктура данных без изменения логики сайта: скрипты захвата/восстановления/проверки снапшота (zip-артефакт вне git), документация по развёртыванию с нуля из снапшота. Демо-сид `db:seed` и проверка `db:check` остаются без изменений
**Зависимости:** этапы 1–6 выполнены и приёмлены. Коммит приёмки Этапа 6 — `85945f4`
**Связанные пункты плана:** `plan-2.md` §0 (золотые правила), §4 (SQLite, структура `scripts/`), §5 (модель данных), §8 Этап 7 (T-7.2 бэкапы, T-7.3 инструкция деплоя — эта задача закрывает только механику, не обвязку), §9 Q-5; `plan2stage6.md` решение №2 (все изображения локальные в `public/uploads/`)
**Версия плана:** `plan-2.md` (итерация 2) + `plan-finances2.md` — единственные действующие

## Цель

Дать второй вариант развёртывания «с нуля» — не демо-сид из макета, а слепок текущего боевого состояния:

1. **Захват** (`snapshot:capture`): согласованная копия живой SQLite-БД + весь каталог `public/uploads/` + манифест → zip-артефакт `julcraft-snapshot-*.zip` (в git не попадает, переносится на сервер вручную).
2. **Восстановление** (`snapshot:restore`): развёртывание из артефакта на чистом сервере (и поверх существующего состояния с защитой и автобэкапом), с докатом миграций при необходимости.
3. **Проверка** (`snapshot:check`): проверка целостности восстановленного состояния (БД + ссылки на файлы + settings) — отдельная от `db:check`, который остаётся сверкой демо-сида с макетом (D-11).
4. **Документация**: инструкция `docs/deploy-snapshot.md` — полный цикл развёртывания с нуля из снапшота.

Итог: два равноправных варианта — **А)** `db:seed` + `db:check` (демо из макета), **Б)** снапшот-артефакт + `snapshot:restore` + `snapshot:check` (боевое состояние).

## Золотые правила (§0 плана) — обязательны

1. `mockup/` и CSS/JS скинов не трогать вообще: задача не затрагивает вёрстку.
2. **Живая БД `site/julcraft.db` — боевой экземпляр, не пересиживать.** Перед началом работы — снять ручную копию файла. Любые тесты, требующие чистой БД (в т.ч. регресс демо-сида), выполнять с переопределением: `DATABASE_URL=file:./tmp-seedtest.db npm run db:seed && DATABASE_URL=file:./tmp-seedtest.db npm run db:check`. Запуск `npm run db:seed` без переопределения `DATABASE_URL` в этой задаче запрещён.
3. Скрипты кроссплатформенные (рабочая машина Win11, целевой сервер — Ubuntu из Этапа 7): никакого PowerShell/cmd-специфичного кода, только Node API и библиотеки.
4. Существующий поток `db:seed` / `db:check` / `db:migrate` не ломать: их поведение и вывод не меняются.
5. Коммиты — только по явной команде руководителя.

## Контекст (состояние на 2026-09-04)

- **Стек:** Next.js 16 + TS + Drizzle + SQLite (`better-sqlite3`), скрипты через `tsx` из `site/` (см. `package.json`: `db:generate`, `db:migrate`, `db:seed`, `db:check`). Окружение: Win11, Node v24.
- **Путь БД:** `site/lib/db.ts` (строки 6–13): `resolveDbPath(process.env.DATABASE_URL ?? "file:./julcraft.db")` — `file:` префикс разворачивается от `process.cwd()` (для npm-скриптов это `site/`). `resolveDbPath` не экспортирован; импорт `lib/db.ts` открывает БД (побочный эффект) — для скриптов путь нужно вычислять без открытия БД.
- **Живая БД `site/julcraft.db`** (76 КБ, обновлена 2026-09-04): применены 3 миграции (журнал `drizzle/meta/_journal.json`, последняя `0002_green_ricochet` от 2026-08-24; счётчик строк `__drizzle_migrations` = 3); таблицы: categories (10), componentTypes (6), slotTemplates (28), components (25), products (17), orders (8), settings (включая `telegram.*` с реальным токеном); sqlite_sequence: categories=14, componentTypes=6, slotTemplates=28, components=25, products=19, orders=24 (всего создано, часть удалена — норма). У 1 заявки заполнен `collagePath`.
- **Каталог изображений `site/public/uploads/`**: 209 файлов, 92,4 МБ — `products/`, `components/`, `categories/`, `collages/` + `about-workshop.jpg`. В git трекаются только 27 файлов `components/` (25 SVG + 2 PNG); остальное игнорируется (`site/.gitignore`: `public/uploads/`). В БД хранятся локальные пути: `products.images` (JSON-массив), `components.photo`, `categories.image`, `orders.collagePath`.
- **`db:check` на живой БД даёт 4 FAIL** (workPrice/валюта, orderDays «Вечера на Радищева», photo→SVG, phone) — владелец штатно менял данные через админку; `check-seed.ts` проверяет соответствие макету, а не целостность. Это норма и причина решения №3.
- **Авторизация** — env (D-12), пользователей в БД нет; `.env` в снапшот не входит.
- Существующий ручной бэкап `site/siteDB_31-08-2026.zip` (92 МБ, в git не входит благодаря `site/*.zip` в корневом `.gitignore`) — ручной предшественник этой механики, остаётся как история. `docs/deploy*.zip` — журналы сессий, к задаче не относятся.
- Zip-библиотек в зависимостях нет; `node:crypto` (sha256), `node:fs` доступны; `better-sqlite3` имеет метод `sqlite.backup(dest)` — безопасная согласованная копия (в отличие от копирования файла при активном WAL).
- Next.js 16: код задачи — только `site/scripts/` + `site/package.json` + доки; гайды `node_modules/next/dist/docs/` не требуются.

## Шаг 0. Подготовка: бэкап боевой БД и вынос пути БД

1. Скопировать `site/julcraft.db` → `site/julcraft.db.pre-snapshot-task` (обычное копирование файла; `*.db` уже в `site/.gitignore` — проверить, что git его не видит).
2. Создать `site/lib/db-path.ts`: `export function getDbPath(): string` — перенести туда логику `resolveDbPath` + чтение `process.env.DATABASE_URL ?? "file:./julcraft.db"` из `lib/db.ts` (строки 6–12). `lib/db.ts` использует `getDbPath()`, поведение не меняется.
3. Регресс: `DATABASE_URL=file:./tmp-seedtest.db npm run db:seed && DATABASE_URL=file:./tmp-seedtest.db npm run db:check` — OK; после теста удалить `tmp-seedtest.db*`. Живая `julcraft.db` не трогалась (`git status` чист, кроме новых файлов).
4. Приёмка шага: живая БД на месте (8 заявок), новый модуль используется `lib/db.ts`, демо-флоу на временной БД проходит.

## Шаг 1. Захват снапшота (`snapshot:capture`)

1. Установить `adm-zip` (dependencies) и `@types/adm-zip` (devDependencies).
2. `site/scripts/snapshot-capture.ts`:
   - если `getDbPath()` не существует — ошибка «снимать нечего»;
   - согласованная копия БД: `sqlite.backup(<временный файл>)` (не копировать файл напрямую — риск WAL); после — sha256 копии через `node:crypto`, временный файл удалить;
   - счётчики таблиц (categories, componentTypes, slotTemplates, components, products, orders, settings) и `applied` = `SELECT COUNT(*) FROM __drizzle_migrations`;
   - собрать манифест `manifest.json`: версия формата (1), дата создания, git-коммит (`git rev-parse HEAD`, при отсутствии git — null), `db: { sha256, bytes, tables: {…счётчики}, migrationsApplied }`, `uploads: { files, bytes, byFolder: { products, components, categories, collages } }`, `warnings: ["содержит личные данные клиентов (заявки)", "содержит секреты (telegram.botToken) — не публиковать"]`;
   - zip: `manifest.json` + `julcraft.db` (байты копии) + дерево `public/uploads/**` (внутренние пути вида `public/uploads/...` — как в существующем `siteDB_31-08-2026.zip`);
   - имя файла `julcraft-snapshot-YYYY-MM-DD-HHmm.zip` в `process.cwd()` (= `site/`).
3. `package.json`: `"snapshot:capture": "tsx scripts/snapshot-capture.ts"`.
4. Приёмка шага: артефакт создан (~92 МБ); внутри манифест + БД + дерево uploads; sha256 распакованной БД = манифест; `git status` не показывает zip; числа манифеста сходятся с реальностью (209 файлов, 8 заявок и т.д.).

## Шаг 2. Восстановление (`snapshot:restore`)

1. `site/scripts/snapshot-restore.ts`:
   - аргумент — путь к zip (`npm run snapshot:restore -- <path>`); без аргумента — свежайший `julcraft-snapshot-*.zip` в cwd; ошибки — с перечнем доступных;
   - прочитать манифест; поддерживаемая версия формата — иначе ошибка;
   - **чистый сервер:** `getDbPath()` не существует → просто разворачиваем;
   - **поверх существующего:** требует флаг `--force`; перед этим автобэкап: существующий файл БД переименовать в `julcraft.db.bak-<ts>`; `julcraft.db-wal` / `julcraft.db-shm`, если есть, удалить (устаревший WAL от старой БД опасен). Каталог uploads не очищать (см. контекст);
   - распаковка: запись `julcraft.db` — буфером в `getDbPath()` (НЕ в cwd — `DATABASE_URL` может вести в другое место); записи `public/uploads/**` — в `<cwd>/public/uploads/**` (создать папки при отсутствии);
   - сверка после распаковки: sha256 БД = манифест; количество файлов uploads = манифест (при несовпадении из-за мусора в каталоге — WARN с числами, не FAIL);
   - версии схемы (решение №4): `applied` из БД сравнить с числом записей `drizzle/meta/_journal.json`; если в БД больше — ошибка «снапшот снят с более новой версии кода — обновите репозиторий (git pull) и повторите»; иначе `migrate(db, { migrationsFolder: resolve(process.cwd(), "drizzle") })` — докат недостающих;
   - `PRAGMA integrity_check` + `foreign_key_check` — быстрая самопроверка;
   - итоговый вывод: счётчики из манифеста, что куда положено, напоминание: `.env` снапшотом не восстанавливается (ADMIN-доступы, DATABASE_URL, SITE_URL — см. документацию).
2. `package.json`: `"snapshot:restore": "tsx scripts/snapshot-restore.ts"`.
3. Приёмка шага (тесты на рабочей машине, живую БД предварительно забэкапив в Шаге 0):
   - сценарий «с нуля»: переименовать `julcraft.db` и `public/uploads` во временные имена → `snapshot:restore` → БД и каталог на месте, счётчики прежние (10/6/28/25/17/8), `tmp-` копии удалить;
   - сценарий «поверх»: повторный restore без `--force` — отказ; с `--force` — выполнен, создан `julcraft.db.bak-*`;
   - сценарий «откат»: после цикла состояние проверяется `snapshot:check` (Шаг 3) и `npm run dev` — каталог показывает реальные фото, в `/admin/orders` видны 8 заявок с коллажем.

## Шаг 3. Проверка снапшот-состояния (`snapshot:check`)

1. `site/scripts/check-snapshot.ts` — целостность, НЕ сверка с макетом (в стиле `check-seed.ts`: `assert()` с OK/FAIL, `process.exitCode = 1` при провале):
   - БД: `integrity_check` = ok; `foreign_key_check` пуст;
   - ссылки на файлы: каждое `products.images[]` — локальный путь `/uploads/...` на существующий файл; `components.photo`, `categories.image` (не null), `orders.collagePath` (не null) — на существующие файлы;
   - никаких внешних URL: ни одно изображение не начинается с `http://` / `https://`;
   - счётчики: категории/товары/комплектующие/заявки > 0 (цифры — в вывод); слоты у категорий с `hasSlotTemplate`;
   - цены: у всех товаров и комплектующих `price > 0`;
   - settings (`getSettings()`): `contacts.phone/email/address` не пусты, `hours` не пуст, `about.short/history/principles` не пусты; пустые `telegram.*` — WARN (не FAIL);
   - наличие `public/uploads/about-workshop.jpg` и подпапок `products/components/categories/collages`.
2. `package.json`: `"snapshot:check": "tsx scripts/check-snapshot.ts"`.
3. Приёмка шага: на восстановленном состоянии — все OK; негативный тест — временно переименовать один файл из `products/` → FAIL с понятным сообщением → вернуть файл, снова OK.

## Критерии приёмки

1. `npm run snapshot:capture` создаёт `site/julcraft-snapshot-*.zip` (~92 МБ; манифест + БД + `public/uploads/**`), в git не попадает; sha256 и счётчики манифеста сходятся.
2. `npm run snapshot:restore` разворачивает с нуля (БД по `getDbPath()`, каталог uploads воссоздан) и поверх (`--force`, автобэкап, удаление `-wal`/`-shm`); недостающие миграции докатываются; снапшот новее кода — внятная ошибка; без zip/путаного манифеста — корректные ошибки.
3. `npm run snapshot:check` проходит на восстановленном состоянии (integrity, FK, все ссылки на файлы, локальные пути, счётчики, цены, settings) и ловит битое состояние (exitCode 1).
4. Полный цикл на Win11: capture → удалить БД+uploads → restore → check → `npm run dev`: каталог с реальными фото, 8 заявок в админке. Состояние рабочей копии после цикла — то же боевое (БД из снапшота может отличаться байтами от исходной из-за `backup()` — сверять по счётчикам и `snapshot:check`, а не побайтово).
5. Демо-флоу не сломан: `DATABASE_URL=file:./tmp-seedtest.db` цикл seed+check проходит; `npm run build` и `npm run lint` — без новых ошибок; живая `julcraft.db` цела (8 заявок на протяжении всей задачи, копия `.pre-snapshot-task` на месте).
6. `docs/deploy-snapshot.md` и журнал `plan-2.md` обновлены; `mockup/**`, скины и логика сайта не тронуты.
