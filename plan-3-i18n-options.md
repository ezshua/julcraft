# Многоязычная поддержка JulCraft: варианты реализации

> Дата: 2026-09-07
> Назначение: сравнение подходов к i18n для выбора решения руководителем (фиксация в plan-3.md)
> Входные данные: аудит констант — `plan-3-i18n-constants.md`
> Контекст: Next.js 16.3.1 (App Router), SQLite + Drizzle, Auth.js, без Tailwind (собственные скины), SSR-цены из cookie, панель «Вид» (skin-switcher.js), этап 7 (деплой) в проверке

---

## 0. Ключевые вводные (влияют на выбор)

1. **Объём:** ~990 UI-строк с кириллицей, из них витрина ≈320, админка ≈530, API-ошибки ≈130; уникальных ключей витрины ≈250-280 + контент БД (~150 записей: категории, товары, комплектующие, слоты, Settings-тексты).
2. **Контент живёт в БД в одном языке** (`drizzle/schema.ts` — одинарные text-поля; Settings-JSON тоже). UI-словарь решает только половину задачи — вторая половина это **мультиязычная модель данных**.
3. **Золотое правило §0: макет — источник истины 1:1.** Локализация не должна менять вёрстку/классы; переключатель языков должен вписаться в существующий дизайн (панель «Вид», шапка) — это расширение, утверждаемое руководителем.
4. **Морфология:** русские plural («день/дня/дней»), падежи (винительный «Собираем брош...» по slug), дни недели из дат — требуют ICU-сообщений и per-locale правил, не «плоских» словарей.
5. **SEO:** сейчас metadata на русском, sitemap без hreflang, `lang="ru"` в единственном layout.
6. **Админка**: мастер русскоязычный; Telegram-шаблоны — для мастера.
7. **Валюта уже переключаемая** (cookie + `/api/currency`) — паттерн cookie-переключателя уже есть и может быть переиспользован для языка.

---

## 1. Варианты реализации

### Вариант A. next-intl (маршрутизация с префиксом `/[locale]`)

**Как работает.** Стандартный App Router-подход: `app/[locale]/...`, middleware редиректит `/` → `/ru` (или по `Accept-Language`/cookie), словари `messages/ru.json|en.json|...`, серверный `getTranslations()` + клиентский `useTranslations()`, ICU-синтаксис для plural (решает «день/дня/дней» из коробки).

**Что даёт:**
- Лучший SEO: отдельные URL на язык, `generateMetadata` per-locale, `hreflang` в sitemap.
- Полноценные ICU-сообщения: `{days, plural, one {день} few {дня} other {дней}}`.
- Перевод **контента БД** решается параллельно: `name` → `name_ru/name_en` (миграция Drizzle) или JSON-поле `name: {ru, en}`; перевод показывается по активной локали, фолбэк — базовый язык.

**Трудозатраты:**
- Реструктуризация `app/`: перенос всех маршрутов в `app/[locale]/` (public, admin, api остаются вне locale). Механический, но широкий рефакторинг ~60 файлов.
- Все `metadata`/`sitemap.ts`/`robots.ts` дорабатываются под locale.
- `<html lang>` — динамический из locale (layout в `[locale]`).
- Модерация hreflang/duplicate-content — умеренная.

**Оценка:** витрина RU+EN — ~2-3 недели работы агента; каждый следующий язык — +словарь (~250 ключей) + переводы контента.
**Риски:** самый большой рефакторинг из всех вариантов; нужно аккуратно пронести правила «копия макета» (классы не меняются — меняются только строки).
**Когда выбирать:** если нужны индексируемые языковые версии (долгосрочная SEO-стратегия, аудитория из поиска).

---

### Вариант B. Cookie-based i18n без смены URL (собственная тонкая обвязка)

**Как работает.** По образцу существующей валюты: язык хранится в cookie `julcraft-locale` (+localStorage), переключатель в панели «Вид» или в шапке; `layout.tsx` читает cookie → `<html lang>`; серверные компоненты получают словарь через `getDictionary(locale)` (свой `lib/i18n.ts` с типизированными JSON или объекта). URL один на все языки.

**Что даёт:**
- Нулевая реструктуризация маршрутов: правки точечные, в существующих файлах.
- Переиспользование паттерна переключателя (skin-switcher.js уже умеет cookie+reload — добавить кнопку языка туда же).
- Словари — простые TS-модули (`lib/dictionaries/ru.ts, en.ts`), типизация на TS-типах ключей, никакой новой зависимости.

**Ограничения:**
- SEO-дубли: одна URL-версия отдаёт разный контент по cookie → поисковики индексируют только дефолтный язык. Приемлемо, если иноязычная версия — «удобство для гостя», а не канал привлечения.
- `metadata` и `sitemap` — на дефолтном языке (можно развить: `?lang=en`-параметр для соцсетей — опционально).
- Словари без ICU «из коробки»: нужен свой `plural()` per-locale (уже есть для русского — обобщить: `plural(n, {one, few, many})`).

**Оценка:** RU+EN — ~1-1.5 недели; каждый язык — +словарь.
**Риски:** hydration mismatch (сервер рендерит по cookie — уже решено для валюты, тот же механизм); рост сложности, если позже всё же понадобятся локализованные URL (миграция на вариант A/D).
**Когда выбирать:** языки нужны «для удобства» (аудитория — русско/украино/англоязычные гости мастерской), SEO-мультиязычность не критична, скорость внедрения важна.

---

### Вариант C. react-i18next / i18next (клиентская библиотека)

**Как работает.** Классический i18next с React-обвязкой: ресурсы JSON, `useTranslation('namespace')`, `Trans>` для интерполяции, `i18next-icu` при необходимости.

**Что даёт:**
- Зрелая экосистема, знакомая многим, богатые форматы (ICU, sprintf, context — падежи).
- Браузерная детекция языка, мгновенное переключение без reload.

**Ограничения (в нашем стеке):**
- Заточен под SPA/CSR: серверные компоненты Next.js App Router рендерятся на сервере — i18next там работает через костыли (`i18next-http-backend`/ручная инициализация per-request); **проект на 80% серверные компоненты** (SSR-цены, БД) — основная выгода «мгновенного клиентского переключения» не нужна, а интеграция в RSC нестандартна.
- +2 зависимости и runtime-слой, который в App Router обычно заменяют next-intl/своим словарём.

**Оценка:** сопоставимо с B по объёму словарей, но выше по интеграционному риску.
**Когда выбирать:** если бы проект был CSR-heavy; здесь — не рекомендуется.

---

### Вариант D. Внешняя платформа переводов (Lokalise/Phrase/Crowdin) + любой рантайм

**Как работает.** Ключи и словари живут в облачном редакторе; переводчики (или сам мастер) правят тексты в UI платформы; CLI/API синхронизирует с репозиторием; рантайм — любой из A/B.

**Что даёт:**
- Комфортная работа с переводами для нетехнических участников (мастер может поправить текст сам, без PR).
- Контекст-скриншоты, автоперевод-подсказки, история изменений.

**Ограничения:**
- Облачная подписка ($$) и внешняя зависимость для маленького проекта — избыточно.
- Контент БД (товары/категории) платформой не покрывается — всё равно нужна модель данных.

**Оценка:** рантайм (A или B) + обвязка синхронизации; выигрыш только при 3+ языках и активных переводчиках.
**Когда выбирать:** при планах на много языков с внешними переводчиками. На старте — отложить.

---

### Вариант E. Минимальный «быстрый» уровень: только переключаемые тексты Settings (без словарей UI)

**Как работает.** Не трогаем UI-строки вообще. Расширяем только динамический контент: Settings получает параллельные поля (`about.short.en`, `contacts.hours.en`...), в админке — вторая вкладка/поля «English», переключение — по тому же cookie-механизму.

**Что даёт:** главный «маркетинговый» контент (чек знакомства, принципы, о мастерской, часы, адрес) — на 2 языках; кнопки/подписи/бейджи остаются русскими.

**Ограничения:** полумера — гость видит смесь языков («Buy» рядом с «резерв до пятницы»); годится только как временный шаг или если аудитория EN читает по-русски.

**Оценка:** ~3-4 дня. 
**Когда выбирать:** как первый инкремент в связке с B (сделать E → потом добавить UI-словарь), либо если признано достаточным.

## 3. Схема данных для контента (общая для A/B)

Независимо от рантайма, контентной модели нужны изменения. Два подхода:

**Подход 1 — параллельные колонки:** `products.name` → `nameRu/nameEn` (+ `descriptionRu/En`...). 
- Плюс: простые запросы Drizzle, явные поля.
- Минус: миграция всех текстовых полей (категории, товары, комплектующие, слоты, типы), широкие таблицы, каждый новый язык = новая колонка.

**Подход 2 — JSON-поля с локализуемыми значениями:** `name: '{"ru":"Броши","en":"Brooches"}'` (helper `t(product.name, locale)` с фолбэком на ru).
- Плюс: добавление языка без миграций; поля уже есть, миграция — только данных (конвертация строк в `{ru: ...}`).
- Минус: запросы/сортировка по локализованному имени — вручную; валидация через zod-схему `localizedString`.

**Подход 3 — таблица переводов** (`translations: entityType, entityId, field, locale, value`) — нормализованно, но overkill для SQLite одного мастера.

**Рекомендация:** подход 2 (JSON + helper + фолбэк-цепочка `locale → ru`), Settings-JSON уже хранит вложенные структуры — органично. Механизм: `lib/localize.ts` c `L(text, locale)`; в админке — поля «RU / EN» рядом (расширение модалок без изменения вёрстки, по аналогии с D-13).

## 4. План-схема этапов (предложение, детализируется в plan-3.md после выбора)

1. **Этап i18n-1:** вынос UI-строк витрины в словарь (RU-базовый), `lib/i18n.ts`, `plural()` per-locale, `<html lang>`; переключатель языка (панель «Вид» / шапка). Ничего визуально не меняется (RU=текущие строки).
2. **Этап i18n-2:** модель контента — `localizedString` для категорий/товаров/комплектующих/слотов/Settings, миграция данных, поля EN в админке.
3. **Этап i18n-3:** словарь EN + перевод контента сида/прода; hreflang (если вариант A).
4. **Этап i18n-4 (опционально):** админка и API-ошибки на EN; далее — следующие языки.

Каждый этап — отдельное задание агенту (как plan2stage*.md), приёмка по критериям.

## 6. Рекомендация → УТВЕРЖДЕНО руководителем 2026-09-07

> Решения зафиксированы в `plan-3.md` (D-i18n-1…7): языки **RU+EN+UK**; вариант **B** (cookie-based) подтверждён; **админка локализуется полностью** (изменение против предварительной рекомендации); переключатель — в панели «Вид»; дефолты скин+валюта+язык — из `.env`; SEO: ручной ввод как есть, автогенерация — транслит EN, статические страницы — EN-копирайт. Этапность: i18n-1…6 (см. plan-3.md §4).

**Вариант B (cookie-based, собственный тонкий слой) + подход 2 (JSON-локализация контента) + этапность i18n-1..i18n-4**, с возможностью миграции на A (next-intl) позже, если появятся SEO-требования — словари и локализованные данные переносимы без потерь.

Обоснование: минимальный риск, ноль новых зависимостей, переиспользование проверенного cookie-механизма валюты, сохранение правила «копия макета» (переключатель встраивается в существующую панель «Вид»).
