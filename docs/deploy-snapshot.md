# Развёртывание с нуля из снапшота (JulCraft)

> Инструкция по полному циклу: снятие снапшота боевого состояния на рабочей
> машине → развёртывание на чистом сервере (Ubuntu 24.04) из zip-артефакта.
> Второй вариант сида: вариант А — `db:seed` + `db:check` (демо из макета);
> вариант Б (эта инструкция) — снапшот реального состояния.

## Что такое снапшот

Артефакт `julcraft-snapshot-YYYY-MM-DD-HHmm.zip` (~92 МБ) — полный слепок
боевого состояния сайта:

- `julcraft.db` — согласованная копия SQLite-БД (снята через `sqlite.backup()`,
  не побайтовым копированием — безопасно при активном WAL);
- `public/uploads/**` — весь каталог изображений (products, components,
  categories, collages, about-workshop.jpg);
- `manifest.json` — счётчики таблиц, sha256 БД, дата, git-коммит, предупреждения.

**ВАЖНО — секреты и личные данные.** Снапшот содержит:

- заявки клиентов с именами и контактами (orders);
- токен Telegram-бота (`telegram.botToken` в settings).

Артефакт **нельзя публиковать** и передавать по открытым каналам — только
scp/носитель по защищённому каналу. Обезличенный снапшот — в backlog.

В git артефакт не попадает (игнор `site/*.zip` в корневом `.gitignore`).

## 0. Необходимое на сервере (Ubuntu 24.04)

- Node.js LTS (проверено на Node 24) — например, через nvm;
- git;
- артефакт `julcraft-snapshot-*.zip`, перенесённый на сервер (scp/носитель);
- доступ к сети npm (для `npm ci`).

```bash
# проверка окружения
node --version   # ожидается v20+ (LTS)
git --version
```

## 1. Клонирование и зависимости

```bash
git clone <репозиторий-julcraft> julcraft
cd julcraft/site
npm ci
```

## 2. Файл .env

Снапшот **не восстанавливает** `.env` — секреты авторизации в БД не хранятся
(D-12). Создайте его из примера:

```bash
cp .env.example .env
nano .env
```

Обязательные поля:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | путь к БД; по умолчанию `file:./julcraft.db` (от `site/`) — можно не менять |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | доступ к `/admin` и `/api/admin/*` |
| `AUTH_SECRET` | секрет сессий NextAuth: `openssl rand -base64 32` |
| `SITE_URL` | публичный URL сайта (для sitemap, OG, canonical) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | дублируют значения из настроек — используются как env-приоритет для уведомлений |

## 3. Перенос артефакта и восстановление

Артефакт положите в любое место на сервере (например, `/tmp/`); restore
принимает путь аргументом:

```bash
npm run snapshot:restore -- /tmp/julcraft-snapshot-2026-09-04-1356.zip
```

Без аргумента скрипт возьмёт свежайший `julcraft-snapshot-*.zip` в текущем
каталоге (`site/`).

Что делает restore:

- разворачивает БД по пути из `DATABASE_URL` (по умолчанию `site/julcraft.db`);
- распаковывает `public/uploads/**` в `site/public/uploads/`;
- сверяет sha256 БД с манифестом;
- **если БД в артефакте снята с более новой версии кода** (в ней применено
  больше миграций, чем в `drizzle/meta/_journal.json` репозитория) — останавливается
  с ошибкой: сначала `git pull`, затем повторить restore;
- иначе докатывает недостающие миграции (`migrate()` идемпотентен);
- выполняет `PRAGMA integrity_check` и `foreign_key_check`.

**Восстановление поверх существующего состояния** — только с флагом:
`npm run snapshot:restore -- --force /path/to/zip`. Перед этим автоматически:
старая БД переименовывается в `julcraft.db.bak-<ts>`, её `-wal`/`-shm`
файлы удаляются (устаревший WAL от другой БД опасен). Каталог uploads НЕ
очищается — restore не удаляет лишние файлы, при несовпадении количества
выводится WARN.

**Восстанавливайте при остановленном приложении** (иначе процесс держит
открытой старую БД/WAL). Убедитесь, что `npm run start` не запущен.

## 4. Проверка целостности

```bash
npm run snapshot:check
```

Проверяет (это отдельная проверка от `db:check`, который сверяет демо-сид
с макетом D-11): integrity/FK SQLite, все ссылки на изображения из БД —
локальные пути `/uploads/…` на существующие файлы (товары, комплектующие,
категории, коллажи заявок), отсутствие внешних URL, ненулевые счётчики и
цены, заполненность settings, наличие подпапок uploads. При провале —
`exitCode 1` со списком битых ссылок.

## 5. Сборка и запуск

Порядок важен: **restore ДО build** — sitemap и пререндеры читают БД при
сборке, им нужно уже восстановленное состояние.

```bash
npm run build
npm run start   # или под PM2 — см. Этап 7 (T-7.1)
```

Демо-проверка запуска (по аналогии с T-7.3): откройте сайт, убедитесь, что
каталог показывает реальные фотографии, страница контактов — реальные
данные; зайдите в `/admin` (логин/пароль из `.env`) → «Заявки» — видны
заявки из снапшота (с коллажем у заявки, где он был).

## Регламент обновления снапшотов

- Снимайте снапшот **перед значимыми изменениями** (деплой новой версии,
  массовые правки через админку) и по расписанию — регулярная крон-обвязка
  входит в Этап 7 (T-7.2), эта механика её закрывает с технической стороны.
- Команда на рабочей машине (из `site/`):

  ```bash
  npm run snapshot:capture
  ```

  создаёт `julcraft-snapshot-YYYY-MM-DD-HHmm.zip` в `site/` и печатает
  счётчики манифеста. Артефакт сразу уберите в хранилище бэкапов.
- Храните несколько поколений артефактов; актуальность определяется по
  штампу в имени и `createdAt` в манифесте.

## Отличие от db:seed (вариант А)

| | А: `db:seed` + `db:check` | Б: снапшот (эта инструкция) |
|---|---|---|
| Данные | демо-копия макета `mockup/` (D-11) | реальное боевое состояние |
| Заявки | нет | все, с коллажами |
| Настройки | дефолтные из сида | реальные (вкл. токен Telegram) |
| Проверка | `db:check` — сверка с макетом | `snapshot:check` — целостность |
| Кому подходит | разработка, демо | прод/сервер, перенос боевого состояния |

## Риски и предостережения

- Артефакт содержит личные данные и секреты (см. выше) — не публиковать.
- Restore не чистит каталог uploads: файлы, на которые не ссылается БД,
  остаются (это WARN в restore и не ошибка).
- Байты восстановленной БД могут отличаться от исходного файла БД (механика
  `backup()`): сверяйте целостность через `snapshot:check` и счётчики
  манифеста, а не побайтово.
- `.env` не входит в снапшот — восстанавливайте вручную (шаг 2).
